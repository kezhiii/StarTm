# 数据按生产者分文件，轨道文件保持 StarTM 那 14 列一字不改

轨道、姿态、热各写各的文件。轨道文件严格沿用 StarTM 的列名和列序，`timestamp` 在前，后面 13 列，时间戳是 14 位 `YYYYMMDDHHMMSS` 字符串。姿态和热各带自己的时间戳列，允许步长比轨道稀。

明知可以往轨道文件后面追加列而 StarTM 不看也不报错（它按列名取值），仍然选择分文件：一是它的解析器拿第一个时刻的行数当总星数，热的步长比轨道稀，塞进同一个文件就得按轨道的行数重复填；二是谁生产谁负责，一个文件多个作者迟早互相踩。

## Consequences

- 每个时刻的行数必须一致，卫星编号 TM0S1、TM0S2、TM0S3 要在数据里给出来，不能靠行序约定。
- 时间戳按字符串排序，只有定宽格式才保证顺序正确。

## Status

部分待修订。2026-10-09 对照《天幕卫星V0总体设计方案》3.1.5，那里要求"各类数据接口均同时记录坐标系名称和物理单位，避免仅依据数据列顺序判断状态含义"，与本 ADR 的"轨道文件保持 StarTM 那 14 列一字不改"直接冲突：14 列里没有坐标系和单位列。待定的是走一份自描述主文件加一份 StarTM 兼容投影，还是放弃让 StarTM 读同一份数据。
