# 对照《天幕卫星仿真系统软件需求 V0.2》：现状与缺口

日期：2026-10-12。依据 `Basedoc/天幕卫星仿真系统软件需求_V0.2.md`（2026-10-10）逐条核对代码与数据实测结果。分支 `sim-system`。文中每条现状都给了文件或数据出处，标"未实现"的是查过代码确认没有，不是没做界面。

## 一、已经完成的内容

### 1. 数据链路（三颗星的 24 小时一秒一帧能跑起来）

| 环节 | 现状 |
|---|---|
| 合成数据生成 | `sim/tools/make_synthetic.py` 一次产出 16 个自描述 CSV（列名/坐标系/单位三行表头），86401 历元 × 1 s × 3 星 = 259203 行/星 |
| 轨道基线 | 取交付的开普勒根数文件实跑：a₀≈6978.137 km（600 km 高度）、i 97.786~97.792°、RAAN 260.830~260.837°、e≈4.1e-5，T0 = 2026-09-13 04:00:00 UTC，时长 86400 s |
| 给三维画面的接口 | `make_projection.py` 反算六根数并导出 StarTM 现成 14 列契约 `timestamp,sat_id,a,e,i,OMG,omg,f,X,Y,Z,Vx,Vy,Vz` |
| 给参数台的传输 | `make_render_bin.py` 把 8 个类别文件转列式二进制（`columns.f32` 59.1 MB + `codes.i16` 2.07 MB + `manifest.json` 偏移表），浏览器只建 Float32Array 视图不解析文本 |
| 降级路径 | `render/` 不在时前端自动退回 60 s 预览 CSV |

实测：接入耗时 0.9 s（含参数台初始化 1.9 s），iframe 堆 141 MB；`columns.f32` 传输 284 ms。`/api/csv-data` 的响应字节已按格式缓存，同进程首次 2.12 s、之后 0.021 s（`f6b8c9a`）。后端 61 个测试通过。

### 2. 真正算出来的物理与几何（可以拿去讨论的数）

- **太阳星历**：astropy `get_sun`（GCRS）+ erfa `c2t06a` 转 J2000，逐秒给太阳单位向量，晨昏线方向由它摆。
- **日照/本影判定**：`make_synthetic.py:242-269` 用日面与地面的圆盘重叠，本影条件 `ψ+α_s ≤ α_e`，日面可见比例取两圆透镜面积。本历元全程 `shadow_state=0`、`sun_ratio≡1`，本影裕度最小 +447.51 km、最大 +600.98 km，与《星编队晨昏轨道 Python》报告第 9 节（日照 86400、半影 0、本影 0）一致。
- **姿态四元数链**：`q_j2b = q_rtn2b ⊗ q_j2rtn`，本体轴 e_R→+Z_B、e_T→+X_B（代码内断言），含一次 60000~60030 s 绕 +Y_B 的 15° 线性机动；三维画面按数据四元数摆模型，`verify_m3.json` PASS（nadir 1.0 / 翼轴 1.0 / 机动 15.0°）。
- **星地几何**：WGS84 椭球站心（合肥 117.2272°E、31.8206°N、10 km），逐秒方位/仰角/斜距/入锥，可见判据 el ≥ 10°；三星共同可见 3885 s 分 3 个窗口。初始斜距 9574.473 km 与报告 9574.5 km 互证。
- **编队几何**：三条边长取 J2000 真实星间距离，实测 0.627~1.369 km 自由漂移（不是保持 1 km）。
- **太阳入射角**：`incidence_deg` 63.54~101.73°，按本体 +Z_B 与日方向算，已落数据。

### 3. 显示与操作（V0.2 §5 的"以三维场景为主体 + 侧边状态 + 底部时间轴曲线"）

- 三维为主、面板降级的仪表式版面；开始/暂停/1× 10× 60× 倍速、走带滑块、时间标尺上画共同可见窗口带与事件单点，点事件可定位。
- 三种视角：全局轨道、目标跟随（相机吊在选中星外侧）、编队近景（1 单位=1 km 的主星视角）；另有"昼侧视角"把相机挪到站址与日下点之间。
- 三颗星可选，点三维画面里的模型也能选（`__simbridge.onPick` 联动参数台），切换选中星保持当前仿真时刻。
- 空值分四态显示（未接入/尚未计算/暂不可用/数据异常），恒 0 的量不出曲线也不出窗口带，不冒充正常。
- 趋势图两条：编队边长对初始构型的偏差（±10 m 允许带）、目标区太阳高度；图可点击定位时间。
- 表2-1 八组 35 行参数全量可查（`sim/config/panels.json`），另加一枚"光照"徽标带本影裕度。
- StarTM 作为被嵌入子系统由外层页面经同源 iframe 驱动（ADR-0002），桥方法 20 余个，含 `__probe` 自检。

### 4. 后端仍在但当前回放链路不用的能力

WebSocket 实时推送 + `PerturbedOrbitPropagator`（J2、大气阻力进 Gauss 方程，日月三体算出后丢弃，积分是根数上一阶欧拉）、灯光排程库表、协议日志。这部分是"实时模式"的旧骨架，与 V0.2 要的"参数一改就重跑"不是一回事，见缺口 §5。

## 二、对照 V0.2 还差什么

### 1. 能源与热控：一个数都还没有，但补数的人不是本系统

V0.2 §2 把"发电、用电、电池电量与温度如何变化"列为三大目标之一，§3 要求展示发电功率、用电功率、SOC 及曲线、关键部位温度及曲线。现状：

- `power.csv` 五列（gen_power / platform_power / payload_power / accum_energy / battery_margin）**全部为空**，`thermal.csv` 四列同样全空，两个文件的"坐标系"表头行写的就是"未计算"（`make_synthetic.py:453-458`）。实测非空值计数：259203 行里 0。
- 代码里没有任何电池充放电积分、没有任何太阳翼效率模型、没有热平衡或热网络。`over_limit` 只是列名，全库无阈值比较。
- 唯一的例外是入射角已经算出来了，但没有任何下游用它——能源缺的那块物理输入其实已经躺在数据里。

**分工（2026-10-12 用户裁决）：这三项不由本组建模型。** 轨道系统已经做好，姿态、能源、热控三项分别交手下三人实现，本系统的责任是**把输入输出接口定义清楚交出去**，再把回流的结果显示出来。文件归属在 `Basedoc/飞行模拟仿真系统-详细方案.md:43-48` 已经划好：`attitude.csv` 给飞控（卫景）、`power.csv` 给能源（郑译飞）、`thermal.csv` 给热控（吕康正），谁生产谁替换自己的文件，轨道文件永远不动。

界面侧的空已经填好（参数表⑥⑦按"尚未计算"显示，不画假曲线），显示接入不需要再改。缺的只剩两件事：接口成文交出去、对方按接口回文件后按类别替换。

### 2. 四项共用时间轴的因果链：本系统这一半已经通，另一半等人接上

V0.2 §3 末段是一条链：轨道决定日照环境 → 姿态影响受照条件 → 设备工作产生耗电与发热 → 能源热控算出电量与温度。现在前四环本系统都有：轨道逐秒位置、日照与入射角（`incidence_deg` 63.54~101.73°）、姿态四元数、设备点亮/熄灭事件与显示频率。断点在最后一环——功率与温度没有生产者交付。

按裁决，本系统要保证的是**链子的接口不断**：把轨道、时刻序列、太阳入射角、姿态、设备工作功率与启停时刻按约定格式发给三位，对方算完按同一时间轴（连续 1 秒、事件按实际时刻）回文件，界面按类别替换即可。这条链不需要本系统写物理，但需要接口里把"谁给谁什么、什么时间基、什么坐标系和单位"写死，否则回来的数对不上时间轴。

### 4. V0.2 §5 的"地面观察视角"：StarTM 里已经实现，工作台没接

`StarTM/web/modules/views/first-person.js` 已经做了相机钉在站心、地平圈、方位每 30°/仰角 30-60-90° 网格、按 el≥0 给卫星着绿/红、可见颗数统计。缺的只是接线：`sim/js/main.js:108-115` 的 `applyView` 只发 `third` 和 `center`，从没发过 `first`；而且 `?bare=1` 模式下方位/仰角的 DOM 控件被隐藏（`index.html:321-328`）。这是当前性价比最高的一条——桥的 `setView` 收任意字符串，`app.js:169` 已处理 `first`。

### 5. V0.2 §5 的"改参数重新运行"与"场景保存、结果导出"

**"改参数重新运行"本轮不做（2026-10-12 用户裁决）**：与 STK 的对接还没做好，轨道参数修改入口要等对接定了再动。下面这些现状留着，开工时当现成的问题清单用。

- 可配置性：`config/default.yaml` 里 `physics` 整段是死配置——推进器从旧的 `config.py` 取常量（`perturbed.py:22-35`），改 YAML 里的 J2/mu/RE/wE 不生效；`satellite_mass/cross_section/drag_coefficient` 连字段都不是，被 Pydantic 丢掉，阻力系数硬编 CD=2.2、质量 300 kg、面积 π/4（`perturbed.py:119-121`）；`constellation_params`、`start_year/month/day`、`propagation.dt` 在 FastAPI 路径里都没人用。
- 运行时改参数：`PUT /api/config/{key}` 只写数据库 `configurations` 表，`AppConfig.load_from_db` 全库无调用，既不重载也不重启推演。**没有"改轨道/姿态/太阳翼/电池/设备功率/热控参数并重跑"的端点。**
- 姿态、太阳翼、电池、热控四类参数在后端配置模型里根本不存在，只以离线合成 CSV 的形式存在。
- 场景保存：未实现。结果导出：未实现（`CsvService` 只读不写，全库无导出端点）。数据库只有 `configurations/protocol_logs/satellites/satellite_neighbors/light_schedules` 五张表，没有场景/运行/结果表，推演出来的轨道只在内存 RingBuffer 里，从不落库。这两条不在本轮裁决免掉的范围内，V0.2 §5 要"支持场景保存与结果导出"，仍是缺口。

### 6. V0.2 §4 的分系统模块粒度对不上

需求列了 8 个分系统、20 多个部件（计算单元 A/B、载荷冷板、发光组件 A/B、太阳翼组件、电池组、电源管理单元、姿控执行机构组、导航单元、推进单元、测控与存储单元、高速数传单元、星间通信单元、星务单元、传热路径、表面热控与隔热、储热单元、主动热控单元、测温单元、主结构、安装板、外部散热面）。

**本轮只考虑热控、飞控、能源控制三块，粒度待确认（2026-10-12 用户裁决）**，其余分系统先不进数据模型。对应到文件就是三份：`thermal.csv`（吕康正）、`attitude.csv` 与 `flight_ctrl.csv`（卫景）、`power.csv`（郑译飞）。现在的形状是每张扁表 4~5 列，没有按部件的字段，也没有 V0.2 §6 要的"设备工作功率+发热量+启停时间"这张简化描述表。粒度一定，字段就跟着定，所以这一条是接口成文的前置。

### 7. 几个看着像物理、其实是常数的量（验收前必须处理）

| 量 | 实情 |
|---|---|
| `formation_geom.drift_R/T/N` | 恒 0.000。参考中心 `rc`（`:97`）与几何中心 `geom_c`（`:123`）取的是同一个均值，差值自己消掉了，看着像"编队保持极好" |

## 三、2026-10-12 用户裁决四条

1. **"改参数重新运行"本轮不做**，与 STK 的对接还没做好，参数修改入口等对接定了再动。
2. **分工不冲突，我此前判断错了。** 轨道系统已经做好；姿态、能源、热控三项交给手下三人实现，本系统的责任是**给他们定义好输入输出接口**并把结果接进显示。所以 V0.2 §6 的"简化姿态与热控模型"不是本组建模，是那三位建模；本系统不存 SOC 状态、不写热平衡。
3. **§4 的分系统本轮只取热控、飞控、能源控制三块，粒度待确认。**
4. **不需要造一个会进地影的场景。** 全程不进影是当前轨道的正常结果，界面照实显示即可。要补的只是事件生成器与日照判定之间的接线（见 §二.7 末行）。
