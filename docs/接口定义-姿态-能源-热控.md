# 姿态 / 能源 / 热控 数据接口定义

日期：2026-10-12。制定方：飞行模拟仿真系统。实现方：飞控（卫景）、能源（郑译飞）、热控（吕康正）。

粒度与接口形状由本系统定，三位只负责按接口实现算法并交回文件。接口一旦发出，改列要走变更，不要各自加列——界面按列名取数，加列不会自动显示，改名会直接把那一格打成"暂不可用"。

本轮只覆盖 V0.2 §4 里的热控、飞控、能源控制三块；计算载荷、显示载荷、测控数传、综合电子、结构系统先不进数据模型，只在设备工作表里作为功率与发热的来源出现。

## 一、通则（三份文件都必须满足）

| 项 | 规定 |
|---|---|
| 文件形态 | UTF-8 文本 CSV，LF 换行，一个生产者一个文件，谁生产谁替换自己的文件，轨道文件不动（ADR-0004） |
| 自描述表头 | 前三行固定为注释：`# 列名: ...` / `# 坐标系: ...` / `# 单位: ...`，逐列对应，第四行才是列名行。坐标系与单位必须逐列写，缺列写 `-` |
| 时间基 | 连续状态量逐秒：`rel_s` 从 0 到 86400 共 86401 个历元，与 `time_ident.csv` 的 `rel_s`/`utcg` 严格一一对应。步长不许改，缺帧不许插值，缺的历元留空 |
| 卫星标识 | `sat_id` 用编号 1/2/3，对应 TM0S1/TM0S2/TM0S3，三颗都要出全 |
| 空值表达 | 整列没算：把该列在"坐标系"行写 `未计算`，数值留空；个别历元没值：留空。两者界面表现不同（"尚未计算" vs "暂不可用"），不要拿 0 或常数填坑 |
| 事件量 | 不进连续文件。启停、切换、超限起止这类单点事件写进 `events.csv`，列定义见 §五 |
| 版本 | 每次交付在 `time_ident.csv` 的 `param_ver` 里带一个可区分的版本号（如 `power-v1`、`power-v2`），界面会在数据源栏显示，出问题时用来对账 |

## 二、本系统给三位的输入

这五份文件已经在跑，格式已定，直接取用，不需要三位回传。

| 文件 | 关键列 | 谁要用 |
|---|---|---|
| `orbit_j2000.csv` | X/Y/Z（J2000, km）、VX/VY/VZ（km/s） | 三位都要 |
| `orbit_itrf.csv` | X/Y/Z（ITRF, km）、经纬高 | 热控（外热流的地反照视角）、飞控 |
| `sun_eclipse.csv` | 太阳 J2000 单位向量、`incidence_deg`（本体 +Z_B 与日方向夹角，实测 63.54~101.73°）、`shadow_state`（0日照/1半影/2本影）、`sun_ratio`（日面可见比例）、`umbra_margin_km`（本影裕度，实测最小 +447.5 km） | 能源主输入，热控次输入 |
| `attitude.csv` | `q_j2b_*`、`q_rtn2b_*` | 卫景交付前由我方合成占位；能源按它算太阳翼受照，热控按它算姿态对散热面朝向的影响 |
| `equipment_duty.csv` | 见 §三 | 能源与热控的**共同**输入，两边必须用同一张表，不要各自假设设备功耗 |

依赖顺序是**飞控 → 能源 → 热控**：卫景的姿态先定，郑译飞的受照角才定；郑译飞的功率平衡先定，吕康正的发热边界才定。三位不要并行猜对方的数。

## 三、设备工作表 `equipment_duty.csv`（新增，本系统出）

V0.2 §6 要求设备"先以工作功率、发热量和启停时间描述"。这张表就是那个描述，也是能源的用电侧与热控的热输入侧唯一的共同源。

列：`sat_id, equip_id, t_start, t_end, duty_mode, standby_w, normal_w, peak_w, sunlit_avg_w, eclipse_avg_w, heat_w, heat_node`

| 列 | 单位/取值 | 说明 |
|---|---|---|
| `equip_id` | 方案表44~55 的单机名 | 一行一台设备的一段连续工作状态 |
| `duty_mode` | 工作 / 待机 / 退出 | "退出"表示该设备在此时段不工作（如显示期间计算载荷停机），**不是零功率**，界面上要能区分 |
| `standby_w` / `normal_w` / `peak_w` | W | 三档功率，直接抄方案表44~55；某档没给就留空 |
| `sunlit_avg_w` / `eclipse_avg_w` | W | 日照期与地影期平均，方案表52 是按这一口径给的（AI 算力载荷），没有就留空 |
| `heat_w` | W | 该段发热量，对应方案表96"单机热耗"；表96 里标"待确认"的就留空 |
| `heat_node` | 热节点 ID | 发热挂到哪个热节点，热控按它加源 |

**数值不用我们编，方案里已经有，而且是逐台单机给的。** 核对方案 4.3 的 11 张设备功耗表（表1~表11），共 **78 台设备**，每台给待机/正常/峰值三档功率（热控那张例外，给的是日照期平均/地影期平均/峰值）。完整清单见 **附录 A**，`equip_id` 就是那张表的编码，由本系统从方案原表逐台抄出，三位不自己加设备名；要加走接口变更。

分系统前缀（附录 A 按此归类）：

| 前缀 | 分系统 | 台数 | 方案原表 |
|---|---|---|---|
| AV | 星务与数据管理 | 7 | 表1 |
| AOC | 姿态与轨道确定 | 8 | 表2 |
| ACE | 姿态控制执行 | 5 | 表3 |
| TC | 测控通信 | 6 | 表4 |
| XDR | 高速数传 | 6 | 表5 |
| AI | AI 计算载荷 | 8 | 表6 |
| DS | 发光演示载荷 | 8 | 表7 |
| PROP | 霍尔推进 | 8 | 表8 |

由此定两条粒度规则：

1. **`equipment_duty.csv` 按单机列，不按 V0.2 §4 的"单元"合并。** 方案的功耗表和热耗表本来就是单机粒度，合并到单元反而把现成的数丢了。V0.2 §4 那张"计算单元 A/B、载荷冷板"式的清单只用于**分系统归类对照**，不作为数据行。
2. **功率按方案给三档**：`standby_w` / `normal_w` / `peak_w`；热控那九台另填 `sunlit_avg_w` / `eclipse_avg_w`（方案表9 就是这个口径）。`heat_w` 单独一列，对应方案热耗表（表96）的"单机热耗"，那里标"待确认"的就留空。

**附录 A 核对时发现两处方案的自相矛盾，得往上提：**

- **星间激光通信终端在功耗表里根本没有条目。** 方案别处写明"星间通信终端 每星两套 分别面向沿轨前、后相邻节点建链"，热耗表也列了"激光终端1/激光终端2"（单机热耗标"待确认，终端方提供"），但 11 张功耗表 78 台里没有它。结果是**热控要按它发热建模，能源却没有它的功率数**。归口：罗新辉或陈宇航补功耗，或明确它按 XDR/TC 的哪一项计入。
- **发光单元的工作说明写"仅在地影演示时工作"**，而当前晨昏轨道 24 h 全程零地影（本影裕度最小 +447.5 km）。这条与 ADR-0005"显示阶段只按几何可见排、地影不参与判定"直接对撞，也就是遗留事项 2（显示是否要求天黑）的另一份证据。若按表7 那句执行，本场景下发光载荷永不点亮。归口：罗新辉裁决。

## 四、三位分别交回什么

### 4.1 飞控（卫景）— `attitude.csv` + `flight_ctrl.csv`

`attitude.csv` 列已存在，保持不动，只钉三件事：

| 列 | 单位 | 口径规定 |
|---|---|---|
| `q_j2b_x/y/z/w` | 无量纲 | J2000→本体四元数，必须归一化（交回后本系统校验 \|q\|−1 < 1e-6）。分量顺序 x,y,z,w，实部在最后 |
| `q_rtn2b_x/y/z/w` | 无量纲 | RTN→本体，RTN 原点是编队参考中心这个虚拟点，不是任一颗星 |
| `wx/wy/wz` | rad/s | **本体轴**角速度，由四元数微分得到，不要填姿态角的差分 |
| `att_mode` | 字符串 | 取值限定：`nadir`（对地）、`sun`（对日）、`inertial`（惯性定向）、`maneuver`（机动中）。新增值先报本系统，界面按值上色 |
| `stable` | 0/1 | 姿态指向稳定判据由飞控定，但要把判据写进交付说明，界面上要能悬停显示"按什么算稳定" |

`flight_ctrl.csv` 的口径以**表3-6「飞控输入与执行」行为准**：RTN 三轴指令、限幅及实际加速度、控制器状态，编队 RTN 坐标系，单位 m/s²；「控制代价」行为单次/累计速度增量（m/s）与控制次数（次）。现有表头写的 RTN + m/s² 是**对的**，错在合成数据往 `cmd_ay` 里塞了机动的角速率（15°/30 s 化弧度 = 0.0087266）——那是占位数据的锅，不是列定义的锅。本文件早前一版把单位改成本体 rad/s²，那是我没查表3-6 就自己定，**作废**。

| 列 | 单位 | 口径（表3-6） |
|---|---|---|
| `cmd_ax/ay/az` | m/s² | 编队 RTN 三轴指令加速度 |
| `cmd_limit_x/y/z` | m/s² | **新增**。指令限幅，表3-6 明列"限幅" |
| `act_ax/ay/az` | m/s² | 实际加速度，与指令分开，两者不等才有控制量可看 |
| `ctrl_state` | 字符串 | **新增**。控制器状态（表3-6 要求），取值随交付说明给 |
| `ctrl_count` | 次 | 控制次数，区分保持、任务调整和恢复阶段 |
| `dv_single` | m/s | **新增**。单次速度增量（表3-6 有这一项） |
| `accum_dv` | m/s | 累计速度增量，**必须是速度增量不是角度**；无推进动作就留空 |

### 4.2 能源（郑译飞）— `power.csv`

表3-6「能源状态」行规定的项是：**发电功率、平台功率、载荷功率、累计耗能、电量裕度**，单位 W、Wh、%。现有五列正好对上，语义钉死如下，另按 V0.2 §3 补两列：

| 列 | 单位 | 口径 |
|---|---|---|
| `gen_power` | W | 太阳翼阵输出功率，整星合计。受照条件用 §4.2.1 的 `array_incidence_deg` 与 `array_proj_factor`（表3-6 已把这两项列为我方输出），日面可见比例用 `sun_ratio`，不要自己再算一遍太阳位置 |
| `platform_power` | W | 平台用电，来自 `equipment_duty.csv` |
| `payload_power` | W | 载荷用电（计算载荷+显示载荷），来自 `equipment_duty.csv` |
| `accum_energy` | Wh | **累计耗能**（表3-6 原义，单调不减），不是电池储能量——本文件早前一版写成"储能量"，作废 |
| `battery_margin` | % | 电量裕度，负值即跌破下限，界面转红并计入超限数 |
| `batt_power` | W | **V0.2 扩展**（表3-6 无此项）。电池充放电功率，充电为正、放电为负 |
| `battery_soc_pct` | % | **V0.2 扩展**。电池荷电状态，V0.2 §3 点名要 SOC 曲线；与 `battery_margin` 的换算关系（容量基准、裕度定义在 SOC 上的哪一点）随交付说明给 |

现成的基准不用另起：方案**表 11-x「工作模式功率平衡」**已给出平台待机 / AI 峰值 / 发光演示三种模式的设备端与电源源端、日照与地影功率（如平台待机 150 / 约167 / 200 / 约222 W），**蓄电池充放电倍率与组电流表**也在同一章。请以此为对照，差异写进交付说明。

模型要求：逐秒推进，电池要有积分过程，不接受"解析拟合出来的正弦"。若某段不工作（`duty_mode=退出`），该设备功率按 0 计入但 `platform_power`/`payload_power` 仍要给出整星合计。

#### 4.2.1 太阳翼受光：按 4.1 的布局，这条轨道的固定翼只能拿到理想值的 16%

设计依据（《总体设计方案》4.1）：太阳翼**沿 ±Y 方向展开**、一对可展开太阳翼为整星提供电能，整体布局为"中央设备与热控核心—±Y 太阳翼—+Z 通信与散热—−Z 对地发光—X 向电推进"。

由此定死一条几何：面板沿 ±Y 展开，则 Y 轴在面板平面内，**法向必然垂直于 Y_B**。而实测（259203 历元，姿态四元数与交付的 `incidence_deg` 逐历元比对，最大差 5.6e-7°，口径确认一致）：

| 量 | 实测 |
|---|---|
| 太阳方向在 ±Y_B 上的分量 \|cos\| | 平均 **0.9703**，最小 0.8952 → 太阳几乎顺着翼展方向来，面板侧棱对着太阳 |
| 法向取 +Z_B（天顶）| 平均 \|cos\| = **0.1640**，入射角 63.54°~101.73°、平均 85.44° |
| 法向取 +X_B（沿轨）| 平均 0.1270 |
| 固定法向的最优方向 | 与 +Z_B 相差不到 2°，即天顶方向就是最优，平均 0.1640 |
| 允许绕 Y_B 单轴跟踪（法向在 X_B-Z_B 平面内自由转）| 平均 **0.2268**，最差历元仍有 0.0615 |

结论给能源：**固定翼最好也只有理想受光的 16.4%，加单轴跟踪到 22.7%**。这不是接口能解决的，是设计输入，三条路选一条：①按 16%/22.7% 重算 4.3.4 的能源指标与电池容量；②改翼展方向（例如沿 ±X 或 ±Z 展开，让面板平面能朝日）；③改姿态策略（对日定向，但那样 −Z 发光面对地就保不住，牵动显示任务）。选哪条由郑译飞提、罗新辉与卫景确认，本系统按结论出 `array_incidence_deg`。

接口侧的处理——**这两项本来就是我们的责任，不是能源的输入选择**。表3-6「太阳几何」行要求输出：J2000 太阳方向、本体系太阳方向、**太阳翼法向**、太阳入射角；「地影状态」行要求输出：太阳圆面可见比例、**有效投影系数**、日照/半影/本影状态。对照现在 `sun_eclipse.csv` 的列，缺三样，我方补：

| 补的列 | 单位 | 内容 |
|---|---|---|
| `array_normal_x/y/z` | 无量纲 | 太阳翼面板法向，J2000 分量（表3-6 要求，我方按 4.1 布局与姿态四元数算） |
| `array_incidence_deg` | deg | 太阳与面板法向夹角 |
| `array_proj_factor` | 0~1 | 有效投影系数 = \|cos(法向入射角)\|，表3-6 点名列出 |

法向按 4.1 布局默认取 +Z_B（即上表 0.1640 那一档）；若后续改成绕 Y_B 单轴跟踪或对日姿态，法向随之变，三列一起重算，能源只认这三列、不再自己从四元数反推。`incidence_deg`（本体 +Z_B 口径）保留作 V0.2 §3 的显示量，默认法向下两者数值相同，一旦跟踪或对日就会分开。

### 4.3 热控（吕康正）— `thermal.csv`

现在是每星一行四列、全空。粒度定为**按热节点出温度，宽表**：一个节点一列，列名 `temp_<节点ID小写>`。

节点清单不另起一套，直接用《总体设计方案》§11.2.12 温度监测与任务保护那句覆盖要求展开：**计算载荷热接口、激光终端 1 温控安装面、激光终端 2 温控安装面、散热器关键部位、蓄电池**，另留一类"其他温度敏感设备"作开放项。同方案 §11.2 写明"两套激光终端以 1、2 区分，**最终名称和数量按总体设备清单统一**"，所以节点数由吕康正按总体设备清单定，本系统不预设数量；定稿前界面按"尚未计算"出空列不报错，加节点算接口变更。

**门限目前没有源头**：方案有一张专门的温度限值表（表 11-x「设备/对象 / 温度范围 / 稳定性或控制阈值 / 状态及依据」），七行对象——星载计算载荷、星间激光通信终端、对地数传设备、对地可见光演示载荷、电源变换与配电设备、星务计算机及其他平台电子设备、蓄电池及低温设备——**每一格都写着"待确认"**，并注明"告警、降频、保护及加热阈值在设备温限明确后，结合测温误差、控制延迟和热分析结果设置"。`over_limit_count` 要判超限就得有门限，所以交付时请连同各节点的允许温度一起给（哪怕先按候选器件资料填一版并标 TBC），否则这一列只能留空，界面上"超限"计数也就一直显示"尚未计算"。

| 列 | 单位 | 口径 |
|---|---|---|
| `temp_<node>` | °C | 该节点逐秒温度。外热流边界用 `sun_eclipse.csv` 与 `orbit_itrf.csv`，不要自定地球反照率 |
| `ext_heatflux` | W/m² | 整星平均外热流（太阳直接 + 地球反照 + 地球红外三项合成），交付说明里写清三项各多少 |
| `equip_power` | W | 进入热模型的设备总发热，必须等于 `equipment_duty.csv` 同历元 `heat_w` 之和，本系统会逐历元核这条等式 |
| `over_limit_count` | 个 | **替换原 `over_limit`**。超限节点个数；原 `over_limit` 是 0/1，多节点时说不清是谁超。门限值随节点清单一起交，界面按门限逐格上色 |
| `temp_max_node` | 部件ID | 当前最热节点，方便列表上一眼看谁在顶上 |

## 五、事件表 `events.csv` 的补充

## 六、交付验收

三位交文件后，本系统跑 `sim/tools/verify_handoff.py` 自动核对，任一条不过就打回，不改对方的数：

1. 历元网格：连续状态文件按"每星每历元一行"，`rel_s` 必须是 0..86400 的连续整秒，行数为 86401 × 星数。事件式文件（`events.csv`、`flight_ctrl.csv`、`equipment_duty.csv`）不按网格要求。
2. 表头三行的列数与数据行列数一致，坐标系/单位行不含空项。值没算可以空着，**单位不能空着**——空着单位等于让对方猜 W 还是 kW。
3. 四元数归一化 \|q\|−1 < 1e-6。
4. 单位量级检查：功率在 ±5 kW 内、温度在 −150~+200 °C 内、SOC 在 0~100% 内，超界视为单位错填。
5. 自洽等式：`equip_power` == Σ `equipment_duty.heat_w`（同历元）；`accum_energy` 与 `battery_soc_pct` 换算一致。
6. `over_limit_count` 与非空 `temp_<node>` 越门限的个数一致。
7. **几何类标志必须带可见性条件。** 光轴与目标的夹角是一条线，目标在卫星脚下与在地球另一面都接近 0°。本系统在改 `q_conj` 时踩到过一次：入锥判据只看 `off_axis ≤ 1°`，会把斜距 13343 km、仰角 −89.8° 的**对跖时刻**判成入锥。所以凡"指向/入锥/可见"类标志，一律要同时要求目标在地平以上。能源与热控若也出方向性判据（如散热面被本体遮挡），同理。

脚本还会顺带出一份**表3-6 覆盖度报告**：22 类逐项标"有值 / 占位 / 空 / 缺"，用来回答"表3-6 能不能全项交付"，也防止恒 0 的占位列被当成算出来的结果。

界面侧不需要为三位改代码：参数表⑥⑦、姿态组、事件表都已按列名取数，空值四态也通了，真值一到就出曲线，没到的格显示"尚未计算"。
