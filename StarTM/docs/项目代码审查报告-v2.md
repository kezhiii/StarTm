### 二、原报告误判项（3 项已排除）

以下 P0 项经核实**不是真实 Bug**，从问题清单中移除：

#### ~~2.1 匈牙利算法标号更新方向反转~~ — 误判

**原报告声称**：`lx[u] + ly[v] - cost[u][v]` 方向错误，算法无法收敛到最优匹配。

**实际情况**：当前代码（`image-processor.js:764-768`）实现如下：

```javascript
// 最小权匹配的标号更新（正确实现）
for (let x = 0; x < n; x++) {
    if (visitedX[x]) lx[x] += delta;   // 已访问 X 节点标号增加
}
for (let y = 0; y < m; y++) {
    if (visitedY[y]) ly[y] -= delta;   // 已访问 Y 节点标号减少
}
```

这是匈牙利算法最小权匹配的标准实现。`lx` 初始化为每行最小值（697-698行），标号更新方向与 cost 矩阵定义一致。原报告作者对代码理解有误。

#### ~~2.3 Math.asin 参数未钳位 — NaN 风险~~ — 误判

**原报告声称**：`ecefToLocal()` 中 `Math.asin` 的参数未钳位到 `[-1, 1]`。

**实际情况**：当前代码（`math-utils.js:54-57`）：

```javascript
const range = Math.sqrt(s * s + e * e + zUp * zUp);
if (range === 0) return { az: 0, el: 90, range: 0 };
const el = Math.asin(zUp / range) / DEG;
```

`zUp / range` 中 `range = √(s² + e² + zUp²)`，数学上 `|zUp/range| ≤ 1` 恒成立（直角三角形斜边 ≥ 任一直角边）。此外已有 `range === 0` 的除零保护。**不存在 NaN 风险。**

#### ~~2.5 SAT_SCALE_CENTER = 1 坐标比例错误~~ — 误判

**原报告声称**：卫星 ECI 数据以米为单位（~7,000,000），但 `SAT_SCALE_CENTER = 1` 未做缩放，卫星超出相机视锥。

**实际情况**：
- `config.js:5` 定义 `RE_KM = 6378.137`（km），ECI 坐标单位为 **km**（与轨道力学惯例一致）
- `center-person.js` 地球模型使用 `RE_KM`（km 单位），`SAT_SCALE_CENTER = 1` 意味着 1:1 映射
- 主星视角的卫星坐标与地球模型在同一量级，不存在"超出视锥"问题

### 三、P0 — 关键 Bug / 逻辑错误（7 项）

#### 3.1 方位角编队缩放存在 0/360 度环绕错误 ✅

**文件**: `views/first-person.js` 第 261 行、第 508 行

当编队跨越方位角 0/360 度边界时，角度差值未规范化。例如 `local.az = 359, centerAz = 1` 时差值为 358 度（应为 -2 度），乘以 `FORMATION_SCALE = 5` 后变为 1790 度，卫星被放到完全错误的天空位置。CSV 和 WS 两个版本均受影响。

```javascript
// 第 261 行 — 角度差未规范化
const azR = centerAz * DEG + (local.az * DEG - centerAz * DEG) * FORMATION_SCALE;
//                           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//                           跨越 0/360 边界时差值接近 360 度而非接近 0 度
```

**修复方案**：差值规范化到 `[-180, 180]`：
```javascript
let dAz = (local.az - centerAz);
if (dAz > 180) dAz -= 360;
if (dAz < -180) dAz += 360;
const azR = centerAz * DEG + dAz * DEG * FORMATION_SCALE;
```

#### 3.2 `mesh.material.disposed` 是无效检查 ✅

**文件**: `light-manager.js` 第 157 行

Three.js 的 `Material` 类没有 `disposed` 属性，此检查永远为 `false`，是失效的安全保护。操作已 dispose 的材质会在 WebGL 内部产生未捕获的错误。

```javascript
if (!mesh.material || mesh.material.disposed || !mesh.parent) {
//                         ^^^^^^^^^^^^^^^^^^ 永远为 undefined
    return;
}
```

**修复方案**：移除 `mesh.material.disposed` 检查，或改用 `mesh.material._disposed`（Three.js 内部标记）。

#### 3.3 `appState.domCache` 始终为 `undefined` — DOM 缓存完全失效 ✅

**文件**: 全局问题（8 处读取，0 处赋值）

`appState.domCache` 在 8 个位置被读取（`interpolation.js` 3处、`first-person.js` 3处、`center-person.js` 2处），但从未在活跃代码中赋值。唯一赋值位于死代码 `core/bootstrap.js` 中。所有读取处都有降级到 `getElementById`，但 DOM 缓存优化完全失效，在 60fps 动画循环中产生大量不必要的 DOM 查询。

```javascript
// interpolation.js:71 等 8 处
const domCache = appState.domCache;  // 始终为 undefined
const el = domCache ? domCache.get('coordDisplay') : document.getElementById('coordDisplay');
// 永远走 else 分支
```

#### 3.4 `changeSpeed()` 播放循环竞态条件 ✅

**文件**: `playback-manager.js` 第 896-930 行

`changeSpeed()` 通过 `cancelAnimationFrame` 取消旧循环，但若回调已进入微任务队列，新旧循环可能在一帧内同时执行，导致 `csvState.currentTimeIdx` 被双重递增。且 `changeSpeed` 完全重写了播放循环，与 `startCsvPlayback` 的循环是两套独立实现。

#### 3.5 WebSocket 连接状态竞态 ✅

**文件**: `playback-manager.js` 第 603 行

`connectWebSocket` 的 `onclose` 重连逻辑与外部 `clearWsConnection()` 存在竞态。`onclose` 回调可能被清除后又被设置，导致意外重连或断连后无法正确清理。

#### 3.6 Escape 键监听器泄漏 ✅

**文件**: `constellation-panel.js` 第 366-370 行

`init()` 中注册在 `document` 上的 Escape 键监听器使用匿名函数，无 `removeEventListener` 路径。面板重建后会累积多个监听器。

```javascript
document.addEventListener('keydown', (e) => {
    if (e.key === 'Escape' && isFullscreen) {
        fullscreenBtn.click();
    }
});
// 匿名函数，无法移除
```

#### 3.7 `slider.max` 空指针风险 ✅

**文件**: `ui-manager.js` 第 64 行

`slider` 可能为 `null`（来自 `getElementById`），但未做空检查直接访问 `.max`，会抛出 `TypeError` 中断整个 UI 初始化。

### 四、P1 — 性能问题（13 项）

#### 4.1 `applyAll()` 每帧全量更新所有卫星材质

**文件**: `light-manager.js`

`applyAll()` 在 `third-person.js` 的更新函数中被每帧调用，对所有卫星逐一执行 `_updateSatelliteLight`。对数百颗卫星的巨型星座，这是渲染循环的严重瓶颈。建议改为脏标记增量更新模式。

#### 4.2 第三人称视角每帧 `getElementById`

**文件**: `views/third-person.js`

此文件完全未使用 `domCache` 机制，每帧执行 `document.getElementById('coordDisplay')`。其他视角模块已有 domCache 降级逻辑。

#### 4.3 第一人称视角 2N 次密集坐标转换

**文件**: `views/first-person.js`、`interpolation.js`

第一遍计算编队中心方向、第二遍渲染卫星位置，两遍都对每颗卫星执行 `eciToEcef` + `ecefToLocal` 变换（含大量三角函数）。200 颗卫星 = 400 次/帧密集坐标转换。建议缓存第一遍结果。

#### 4.4 连通域 BFS 使用 `shift()` — O(N) 出队

**文件**: `image-processor.js` 第 200 行

连通域标记 BFS 使用 `Array.shift()` 出队，每次操作 O(N)。对 256×256 图像（65536 像素），最坏情况退化为 O(N²)。建议改为索引递增方案。

#### 4.5 匈牙利算法 BFS 使用 `shift()` — O(N) 出队

**文件**: `image-processor.js` 第 715 行

匈牙利算法内部 BFS 使用 `Array.shift()`。由于 N 通常 <100（卫星数），实际影响较小，但仍是不必要的开销。

#### 4.6 Canvas 渐变对象每帧大量创建

**文件**: `constellation-panel.js`

每颗开灯卫星都调用 `createRadialGradient()`，200 颗卫星全开灯时创建 200 个渐变对象。建议缓存预渲染的发光精灵图。

#### 4.7 WS 数据队列 `shift()` — O(N) 出队

**文件**: `playback-manager.js`

队列裁剪使用 `while > shift()`，`Array.shift()` 对 3600 上限的队列是 O(N) 操作。建议使用环形缓冲区。

#### 4.8 WS 渲染循环以 60fps 运行但有效更新仅 1fps

**文件**: `playback-manager.js`

`RENDER_INTERVAL = 1000ms`（1秒1帧），但 `renderLoop` 使用 `requestAnimationFrame`（约60fps），其余 59 帧重复计算相同的插值进度。

#### 4.9 `farthestPointSample` 中 `splice` 性能问题

**文件**: `math-utils.js`

`splice` 在大数组上是 O(N) 操作，采样阶段频繁调用导致性能退化。应改为 swap-and-pop 方案。

#### 4.10 星空球体几何精度过高

**文件**: `star-field.js`

`SphereGeometry(10000, 64, 32)` 约 4096 个三角面，背景球体从内部观察 32x16 已足够，可减少约 75% 顶点数。

#### 4.11 视角切换三重渲染帧

**文件**: `app.js`

切换到主星视角时连续安排 3 次 `requestAnimationFrame` 渲染，场景状态在三帧之间无变化，第 2、3 次完全冗余。

#### 4.12 CSV 大数据集一次性创建百万对象

**文件**: `csv-manager.js`

10000 帧 × 200 星 = 200 万个对象一次性创建，可能导致主线程卡顿数百毫秒。

#### 4.13 灯光时间线 DOM 大量创建

**文件**: `light-timeline.js`

为每颗卫星创建 DOM 元素（label + input + span），数百颗卫星产生大量 DOM 节点。应考虑虚拟化列表。

### 五、P2 — 代码质量与潜在风险（28 项）

#### 5.1 CSV 解析逻辑跨文件重复（3 处）

**涉及文件**: `csv-manager.js`、`ui-manager.js`、`csv-mode.js`

三处代码几乎完全相同的 CSV 文本解析逻辑。任何列定义变更都需同步修改三处。应抽取为共享的 `parseCsvText(text)` 工具函数。

#### 5.2 日志方案不统一（3 种共存）

| 方案 | 使用者 | 调用次数 |
|------|--------|---------|
| `createLogger()` | 3 个文件 | ~10 次 |
| 自定义 `DBG` 对象 | 5+ 个文件 | ~30 次 |
| 原始 `console.log/warn/error` | 26 个文件 | **149 次** |

`createLogger` 实际采用率不到 7%，且自身存在 Bug：颜色模式下 WARN/ERROR 退化为 `console.log`。

#### 5.3 `constellation-panel.js` 主星状态提取逻辑重复 4 次

`getCurrentObsAngle()`、`getCurrentHillCoords()`、`render()`、`handlePatternUpload()` 四处都有 CSV/WS 分支判断和 GMST 计算，应提取为 `getChiefStateAndGmst()` 公共函数。

#### 5.4 `playback-manager.js` 需要拆分（935 行，5 个职责）

| 职责 | 建议拆分为 |
|------|-----------|
| CSV 播放控制 | `csv-playback.js` |
| WS 播放控制 | `ws-playback.js` |
| WebSocket 连接管理 | `ws-connection.js` |
| 页面可见性处理 | 合并入 ws-connection |
| 统一播放控制 | 保留主文件 |

#### 5.5 输入校验缺失

`parseFloat` 对无效输入返回 NaN 但不抛异常，NaN 静默传播到 Three.js 矩阵变换导致画面消失但无报错。

#### 5.6 `visibilitychange` 监听器累积泄漏

**文件**: `playback-manager.js` 第 603 行

每次 WebSocket 断连/重连都注册新的 `visibilitychange` 监听器，旧监听器无法移除（匿名函数注册在 `document` 上）。

#### 5.7 `interpolateSatellites()` 未校验 `sat_id` 一致性

仅按数组索引匹配前后帧卫星，若后端返回顺序变化，会将卫星 A 的位置插值到卫星 B 上。

#### 5.8 纹理 URL 配置不一致

`config.js` 和 `texture-loader.js` 两处定义了 `TEXTURE_URLS`，月球 URL 不一致。应统一配置来源。

#### 5.9 `app-context.js` resize 监听器无法移除

匿名箭头函数注册 resize 监听，无法后续移除。若 `createAppContext` 被多次调用会导致监听器累积。

#### 5.10 共享材质 `CENTER_SAT_MAT` 未 clone 直接使用

**文件**: `center-person.js`

灯光管理器对该材质的修改直接污染了 `sharedResources` 中的共享材质。从星用了 `.clone()`，主星也应同样处理。

#### 5.11-5.28 其他代码质量问题

包括：未使用的导入、魔术数字硬编码、缺少错误边界、Promise 链缺少 catch、事件监听器注册不规范等。

### 七、架构评估

#### 7.1 三次未完成重构地层堆积

项目存在明显的"重构地层"问题，每次重构创建了新抽象但旧代码未迁移、旧文件未删除：

| 重构方向 | 产物 | 状态 |
|---------|------|------|
| DI/Bootstrap 重构 | bootstrap.js, di-container.js, dom-cache.js | 已放弃，全部死代码 |
| Engine/RenderLoop 抽象 | engine.js, render-loop.js | 已放弃，全部死代码 |
| 视角/模式/UI 模块化 | view-manager.js, view-switcher.js | 已放弃，全部死代码 |

#### 7.2 `app.js` — God Object

`app.js`（424 行）承担过多职责：全局状态创建、渲染循环、场景初始化、视角切换全部逻辑（~180 行）、视图更新代理、完整初始化编排。讽刺的是，`managers/view-manager.js` 中已有完整且更优的视角管理实现（170 行），但从未启用。

#### 7.3 `appState` — 全局可变共享包

`appState` 被直接传递给几乎所有模块，任何模块都能读写任意属性。模块间的耦合完全通过它隐式传递，是一个无类型的"全局变量袋"。

#### 7.4 事件监听器管理缺失

项目中有 5+ 处事件监听器使用匿名函数注册在 `document` 或 `window` 上，无清理路径。长期运行或热更新场景下会造成内存泄漏。
